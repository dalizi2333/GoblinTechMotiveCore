**术语定义混乱：**

| 术语 | 文档中的用法 | 问题 |
|------|-------------|------|

```

│                    Scripture（经文）层面                     │
│  Input / Output — 物品/流体的输入输出（保持普通命名）        │
├─────────────────────────────────────────────────────────────┤
│                      Tick 层面（逐 tick 消耗/产出）          │
│  Offering（祭品）— 燃料/电力/应力/介质的每 tick 消耗        │

└─────────────────────────────────────────────────────────────┘
```

**术语使用规范：**

| 场景 | 正确术语 | 错误用法 |

| 燃料燃烧产出 | `Blessing` | `Output` |

### 问题 3：`ScriptureAptitude` 与 `OfferingBlessingManager` 的协作模式

#### 3.1 修改器分类体系

GTM 的配方修改器分为三类：

| 修改器类型 | 特点 | 设计方式 | 示例 |
|-----------|------|----------|------|
| **通用修改器** | 不依赖机器内部特性，公式固定 | 全局定义 | 基础配方匹配修改器 |
| **专用修改器** | 依赖特定机器内部特性 | 随机器一起定义 | 某机器专属的 EU 消耗公式 |
| **Divine 修改器** | 既不通用（依赖机器特性）也不专用（适用于所有 Divine 机器） | **接口抽象** | `OMNIPRESENT_ASCENSION`、`ASCENSION_BENEDICTION` |

#### 3.2 原则与例外

**标准分层原则：**

```
标准分层（通用修改器遵循）：
┌─────────────────────────────┐
│  ScriptureAptitude.CAP      │  ← 外部接口（配方层面）
│         ↓ 委托              │
│  OfferingBlessingManager    │  ← 内部实现（机器层面）
└─────────────────────────────┘
```

**Divine 修改器的特殊处理：**

`OMNIPRESENT_ASCENSION` / `ASCENSION_BENEDICTION` 是**无法完全遵守分层原则**的特殊修改器：

| 修改器类型 | 是否遵守分层 | 原因 |
|-----------|-------------|------|
| 通用修改器 | ✅ 遵守 | 不依赖机器内部特性 |
| 专用修改器 | ✅ 遵守 | 随机器定义，直接访问机器特性 |
| `OMNIPRESENT_ASCENSION` | ❌ 例外 | 需要访问 `IOmnipresentAvatar.getOmnipresentAvatarLimit()` |
| `ASCENSION_BENEDICTION` | ❌ 例外 | 需要访问 `IAscensionBlessed.getDevotionGrade()` / `getOfferingBlessingManager()` |

#### 3.3 实际调用流程

```
ASCENSION_BENEDICTION 调用流程：
┌─────────────────────────────────────────────────────────────┐
│  1. 检查接口                                                 │
│     if (!(machine instanceof IAscensionBlessed blessed))     │
│         return IDENTITY;  // 不支持的机器直接跳过             │
│                                                              │
│  2. 获取机器能力                                              │
│     int devotionGrade = blessed.getDevotionGrade();          │
│     long maxBosom = blessed.getOfferingBlessingManager()     │
│                             .aggregateMaxBosom();            │
│                                                              │
│  3. 获取配方数据                                              │
│     long demand = ScriptureAptitude.CAP.extractDemand(recipe);│
│                                                              │
│  4. 计算升腾结果                                              │
│     int ascendTimes = calculateAscendTimes(demand, maxBosom);│
└─────────────────────────────────────────────────────────────┘
```

#### 3.4 各组件职责

| 组件 | 职责层次 | 具体职责 | 访问方式 |
|------|---------|----------|----------|
| `IAscensionBlessed` | 能力标识 | 判断机器是否支持升腾 | `machine instanceof IAscensionBlessed` |
| `OfferingBlessingManager` | 机器能力 | 聚合献祭模块的 maxBosom/maxEndurance | `blessed.getOfferingBlessingManager().aggregateMaxBosom()` |
| `ScriptureAptitude.CAP` | 配方数据 | 读取经文的 demand/yield | `ScriptureAptitude.CAP.extractDemand(recipe)` |

#### 3.5 设计意图

这种接口抽象设计的价值：

1. **解耦**：修改器不需要知道具体机器类型，只需检查接口
2. **扩展**：新增 Divine 机器只需实现接口，修改器自动适配
3. **统一**：所有 Divine 机器使用相同的修改器逻辑
4. **灵活**：既不依赖 EU 体系（特殊），又适用于所有 Divine 机器（普遍）

#### 3.6 架构关系总结

```
┌───────────────────────────────────────────────────────────────┐
│                    修改器调用架构                              │
│                                                              │
│  机器 ──(instanceof)──→ 接口 ──(getXxx)──→ 管理器            │
│    │                                                    │     │
│    │                                                    ↓     │
│    └─────────────────→ ScriptureAptitude.CAP ←─────────────┘   │
│                           │                                   │
│                           ↓                                   │
│                      修改器计算逻辑                            │
└───────────────────────────────────────────────────────────────┘
```

## 术语使用建议

### 严格分层原则

1. **配方定义层**：使用 `Input` / `Output` / `demand` / `yield`
2. **机器能力层**：使用 `maxBosom` / `maxEndurance`
3. **逐 tick 执行层**：使用 `Offering` / `Blessing` / `divineOffering` / `divineBlessing`
4. **模块层**：使用 `ThunderOfferingModule` / `FuelOfferingModule` 等

### 避免的混淆

- ❌ 不要说"祭品输入"，要说"燃料输入"或"电力输入"
- ❌ 不要说"祝福输出"，要说"燃料燃烧产出"或"电力转换产出"
- ✅ `Offering` 仅用于描述逐 tick 的能量消耗
- ✅ `Blessing` 仅用于描述逐 tick 的能量产出
- ✅ `Input` / `Output` 用于描述物品/流体的配方层面输入输出
